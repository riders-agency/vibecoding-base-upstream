# Независимость перенесённого сайта от старого движка

## Коротко

Докажите, что перенесённые страницы и данные обслуживает целевой движок. Старую систему используйте в согласованной роли, например для чтения во время импорта.

## Плохо

```text
React выводит iframe старого сайта.
Тексты и цены зашиты в шаблон.
Фотографии и поиск читают старый хост.
Проверили только 200 на главной.
```

## Хорошо

```text
Публичные маршруты UI → API → своя БД.
Медиа сохранены в целевом хранилище.
Для источника существует отдельный импорт.
Старый хост недоступен: сценарии работают.
В переходном режиме маршруты явно разделены.
```

## Почему

Оболочка поверх старой системы сохраняет её задержки, отказы и зависимость от выключения. Хардкод в шаблоне не позволяет управлять перенесённой записью, сравнить версии и повторить импорт.

## Когда применять

Для переноса на отдельную систему. При поэтапной замене часть старых маршрутов может работать в старом движке по заранее согласованной карте. Укажите состояние каждого пути, владельца и условие завершения.

### Требования

- Для каждого публичного и административного маршрута укажите владельца рендера, источник данных, API, медиа и разрешённые внешние зависимости. Отдельно опишите маршрут импорта.
- Используйте согласованную изолированную БД, индекс и медиахранилище. Редактируемые поля, связи, цены, SEO и страницы принадлежат модели проекта. Движок исходного шаблона служит основой для компонентов, схема и контент определяются источником задачи.
- Отслеживайте зависимости в SSR, сетевых запросах браузера, стилях, ссылках, JSON, медиа, фоновых задачах и формах. Переходы на согласованные внешние карты, платежи и документы учитывайте отдельно.
- Любой временный прокси имеет явный охват, владельца, условия выключения и тест. Если требование запрещает runtime-fallback к старой CMS, проверьте отсутствие любых её чтений при обычной работе.
- Отключите доступ к изолированной копии старого источника и пройдите маршруты, поиск, медиа, вход, типовое редактирование и безопасную запись. Сверьте реальные ревизии и сетевые зависимости.
- Если переезжает публичная часть, сохраните область неизменяемой админки и её контракты. Если переезжает админка, проверяйте сохранение операторских сценариев отдельно.

## Пример применения

Туристический сайт загружает снимок из прежней CMS. Клиентские страницы, изображения и заявки обслуживает новая инфраструктура. Тестовая недоступность CMS затрагивает задачу импорта и оставляет уже опубликованный каталог работоспособным.

## Как проверить

- Откройте прямой URL в чистой сессии при отключённом источнике. Проверьте HTML, медиа, сеть и данные карточки.
- Измените тестовую запись в новой админке и проверьте проекцию. Переопубликация движка для значения поля не требуется.
- Проверьте объявленные зоны переходной архитектуры по карте URL. Каждое обращение к legacy объяснено.

## Человек

Утверждает разрешённые зависимости, область замены и срок перехода.

## Агент

Агент инвентаризирует зависимости, выносит импорт из runtime и доказывает независимость целевого сценария.
