# Приёмка перенесённой админки по сценариям

## Коротко

Переносите рабочие процессы редактора целиком, от списка до результата публикации. Аналогичные сущности получают общую модель интерфейса и доступа.

## Плохо

```text
Админка выглядит как магазин с формой.
Все свойства в одном textarea.
Товар можно открыть, вариант нельзя.
Права на раздел проверили только в меню.
```

## Хорошо

```text
Список → карточка → вариант → черновик.
Типизированные поля и медиаредактор.
Предыдущие значения, автор и время видны.
Роль проверена в интерфейсе и API.
```

## Почему

Шапка и таблица могут совпасть визуально, хотя работа редактора требует десятков дополнительных возможностей. Специальный механизм прав для одного раздела усложняет поддержку и скрывает непроверенные действия.

## Когда применять

При переносе, сборке нового раздела на существующем движке и приёмке нового редактора. Уточните различия в задачах, модели публикации и группах доступа.

### Требования

- Инвентаризируйте сущности и действия: поиск, фильтр и сортировка, создание, копирование, изменение, варианты, медиа, просмотр версии, публикация, отмена и архивирование в применимой модели. Список доступных операций сопоставьте с реальными маршрутами и API.
- Используйте общие проверенные таблицы и редакторы для аналогичных записей. Для длинных форм и вариантов выделяйте адресуемый экран с возвратом к фильтру и позиции списка. Для админки определите свою оболочку и навигацию.
- Сопоставляйте тип поля и управление: выбор справочника, число, переключатель, дата, медиа, текст. Загрузка изображений имеет исходный редакторский сценарий, включая поддерживаемые вставку, перетаскивание и загрузку по URL. Поля пути сервера не заменяют загрузку.
- Проверяйте сохранение черновика, привычный порядок свойств, видимое изменение полей, автора, время, отличие агента от человека и возврат версии. Показывайте состояние синхронизации, ошибку и конфликт отдельно.
- Применяйте общую модель `сущность → действие → область/объект`, включая вложенные разделы и отдельные записи. Видимость элементов UI отражает правила API. Проработайте поисковый выбор объектов и объяснение области действия. Запрещённый прямой запрос не сохраняет данные.
- Загрузка списка и фильтры не пересоздают всю оболочку. Используйте контракт прикладного API для предметных действий. Измеряйте отдельно открытие экрана, актуальность строки и время сохранения. Проверяйте мобильный режим и обе темы проекта.

## Пример применения

В магазине справочник брендов использует ту же таблицу, что и товары. Бренд открывается на своём адресе, доступен для поиска и редактирования в пределах роли. Пример варианта товара проверяется отдельно до публикации карточки.

## Как проверить

- Создайте новую запись через обычную роль, добавьте изображение и вариант, измените типизированное поле, перезагрузите страницу. Проверьте черновик, историю и публикацию глазами гостя.
- Повторите операции с ролью просмотра и с правом на один раздел. Проверьте чтение, изменение, экспорт и массовое действие вне области прав по контракту API.
- В нескольких аналогичных разделах проверьте одинаковую настройку столбцов, клик по строке, клавиатуру, возврат из карточки и узкий экран.

## Человек

Утверждает перечень ежедневных действий, права и исключения по конкретной сущности.

## Агент

Агент переиспользует рабочие компоненты и проверяет реальные сценарии для каждой роли.
